同一份 54.74GB 权重，公网单流 56.7 天、千兆内网 7.8 分钟、200G 环网 4.14 秒，差 118 万倍。但搬完还有一跳没人提：校验。同一个 7.39GB 分片，绕缓存纯读 0.64 秒，加 sha256 变 4.81 秒（7.51 倍），54.74GB 口径要 36.7 秒 —— 校验占整条链路九成。8 进程并行 3.95 倍能救回来，MD5 比 SHA-256 慢 2.5 倍。每一跳都给秒数和可复制命令，照着算自己的账。

具体做法

这条链路的四跳是：公网 → 内网 → 目标机盘 → 加载。多数部署笔记写到「文件下完了」就结束，但其实真正决定你今晚能不能跑起来的是第三跳到第四跳之间那一步：校验。

本文全部数字来自同一份真实生产权重分片 7,389,759,032 B，在 DGX Spark #1 上实测。54.74GB 的口径是 Arete-27B BF16 全量，来自仓库 API 逐文件累加，不是估算。

四跳耗时（54.74GB）：公网单流 56.7 天 / 公网 8 路并行更慢（0.3 倍）/ 千兆内网 7.8 分钟 / 200G 环网 8 线程 4.14 秒。最慢和最快差 118 万倍。

校验一跳（同一 7.39GB 分片）：绕缓存纯读 0.64 秒；冷读+sha256 4.81 秒；纯算力口径 3.35 秒。折算到 54.74GB，单核校验 36.7 秒，8 进程 8 秒左右。

所以「部署慢」这件事，先别怪显卡。把这条路量一遍，你会发现自己卡在哪一跳。

失效边界
① 所有 54.74GB 与 510.30GB 的耗时都是实测吞吐的直接除法，不是独立计时；② 所有接收端都是 recv 丢弃数据，没有写盘，所以上表是纯网络/纯计算数字，真实搬完还要加写盘时间；③ Arete-27B 本体未下载未运行，本方案不存在任何该模型的推理速度或 tok/s 数据；④ 200G 单流只有 12.9% 的成因未定位 —— 只证明了「接收缓冲加到 16MB 能从 4.9% 提到 12.9%」，没做窗口梯度扫描，不能说缓冲是唯一原因；⑤ 环网 T=2 档未测，8 线程是甜点这句话只能说 8 比 4 好、比 16 好。
