端侧能不能跑：用 available 做减法，别用 MemTotal

环境与安装 · 4.52 GiB 权重 / 可用 2.079 GiB / 缺口 2.441 GiB / 堆上限 2,112 MiB未标注整理于 2026-11-24 有效期 180d

标称 4G 的 ARM 盒子，MemTotal 报 3.808 GiB，但真正能借给进程的 MemAvailable 只有 2.079 GiB —— 中间 1.7 GiB 被内核与常驻服务占着，不会因为你「想跑大模型」就让位。而且这台 SwapTotal=0：越界不是变慢，是直接 OOM Killed。把 27B 级别的 4.52 GiB 权重放进这道减法，缺口 2.441 GiB，连权重都装不下，跟权重压到多小无关。逐档 128 MiB 触碰实测：available 掉 122~126 MiB，近 1:1，没有可捡的空转空间；单进程堆上限落在 2,048~2,176 MiB。

这条适用于

  • Linux，能读 /proc/meminfo
  • 知道模型权重文件的真实字节数
  • 接受 MemAvailable 是浮动值，复测会有几十 MiB 差异

版本指纹

Debian 12.13 / glibc 2.36 / aarch64 Cortex-A55 ×4；Ubuntu / glibc 2.43 / x86_64 Celeron J3455 ×4

具体做法

端侧判断「能不能跑」最常见的错，是拿  当预算。

`MemTotal` 是机器出厂时那个数（这台 3,993,628 kB = 3.808 GiB）；`MemAvailable` 是此刻内核估算「还能借给新进程多少」的数（这台 2,180,204 kB = 2.079 GiB）。相差 1.7 GiB，而这 1.7 GiB 不会因为你要跑大模型就自动腾出来。
更硬的一条是 `SwapTotal = 0`。没有 swap 的机器越界，失败方式是进程直接消失，不是变慢、不是抛异常。你在有 swap 的开发机上写出来的「能跑」，搬到这类盒子上会静默死掉。

拿 27B 级、权重 4.52 GiB 的模型代入：4.520 > 2.079，缺口 2.441 GiB，连权重都放不下。就算换一台 available 6.391 GiB 的 x86 小机，余量 1.871 GiB 也只解决「放得下」——那台的 CPU 缺 AVX2 与 F16C，三值量化的快路径同样不存在，装得下不等于跑得动。

还有一个反常识：这台 4 核 ARM 盒的顺序读 375.3 MB/s，比同为 4 核的 Celeron J3455 的 98.3 MB/s 快 3.82 倍。慢的从来不是 ARM 指令集，是介质与挂载层。

失效边界
1.  本文所有结论来自内存边界、CPU 特性与读吞吐实测；「跑不动 27B」是内存减法算出来的，不是运行出来的。
2. ，其体积为发布方口径，tok/s 一个都没复现（正文已逐处标注）。
3. ，未取多轮中位；先用 mmap 对已缓存文件测出的 188,022 MB/s 属 page cache 假值，整组作废。
4. （trimafs 映射，可能是 eMMC 或 UFS），只知读写约 370-420 MB/s。
5. ，未做 RSS 阶梯验证；有 swap 那台机的越界行为也未验证。
