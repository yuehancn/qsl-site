下大模型前先算 GB 与 GiB：同一个权重两种口径差一百多 GiB

具体做法

【四个仓库的真实字节（hf-mirror 模型 API 逐文件相加，非按参数量估算）】
· PLaMo 0.8B Q4_K_M：573,126,848 B = 0.57 GB = 0.53 GiB
· Arete-27B BF16：54,743,825,646 B = 54.74 GB = 50.98 GiB
· Qwen3.8-Flash-Next：360,023,343,554 B = 360.02 GB = 335.30 GiB（144 文件 / 131 分片）
· Kimi K3.1 Pro：1,561,355,966,953 B = 1561.36 GB = 1454.13 GiB（96 分片）

【本机三块盘（2026-11-10 实测）】C 盘 1539.6 GiB（装完剩 85.47）/ D 盘 1463.0 GiB（装完剩 8.87）/ NAS 15T 12634.0 GiB（装完剩 11179.87）。

【换算系数为什么是 1.0737】2^30 ÷ 10^9 = 1.073741824。厂商标称按十进制（1 TB = 1000 GB），操作系统按二进制显示（1 TiB = 1024 GiB）。2TB 盘厂商标 2000 GB，系统里显示 1862.6 GiB；4TB 盘标 4000 GB，显示 3725.3 GiB。差异随容量线性放大：0.5 GiB 的模型差 0.03 GiB 无所谓，1454 GiB 的模型差 107 GiB 就是生死线。

【典型误判】某盘 1463.0 GiB 可用，看到模型标「1.5TB」，算成「还差 37GB，清一下就够」。实际 1454.13 与 1463.0 只差 8.87 GiB 余量，装下去系统还要留 10% 空闲，必爆。

【加盘 vs 放 NAS 的成本结构】
· 加 4TB NVMe：系统内 3725.3 GiB，减 1454.13 剩 2271.2 GiB。一次性约一千五。
· 放 NAS：空间 11179.87 GiB 够，但千兆 SMB 顺序读 99.96 MB/s，1454.13 GiB 读一遍 4.34 小时 —— 每次加载都付一次。一个模型一个月重启 1 次，一年 50 小时以上。
结论：能用本地盘就不用 NAS，能加盘就别省那一千五。

失效边界
GB→GiB 统一按 ÷1.0737 换算，未区分厂商实际标称差异（不同品牌 2TB 盘在系统内可能是 1862 或 1863 GiB）。NAS 4.34 小时按 99.96 MB/s 线性折算，未计网络波动与 SMB 开销，实际更长。「系统需留 10% 空闲」是经验值，非硬性规范。四个仓库体积取自平台 API 逐文件相加，若仓库后续增删文件需重取。未实测「装完只剩 8.87 GiB 时系统具体表现」，是按经验推断。
