llama.cpp 线程数：峰值远小于核数，全开反而崩

性能 · 3 机 × 10 档线程 / 1.5B Q4_K_M / 1,117,320,736 B未标注整理于 2026-11-22 有效期 permanent

同一份 1.5B Q4_K_M（1,117,320,736 B）、同一个 llama.cpp b12600，三台机器扫线程数：24 核机上解码峰值在 20 线程（73.83 tok/s），24 线程反而降到 68.16（−7.7%）；80 线程双路机上解码峰值只在 20 线程（29.39 tok/s），开满 80 线程崩到 1.72 tok/s（−94.1%，两次复现 1.72 / 1.94）；ARM GB10 20 核机峰值在 8 线程（91.56），开到 20 线程掉 59.7%。没有任何一台机器的峰值线程数等于核数。预填充的峰值与解码不是一个值：本机 24（1010.93）、双路 40（344.09）、ARM 16（400.68），后两台差一倍。结论：-t 取逻辑核的 1/4 到 1/2，且两阶段要分开配。

llama.cppCPU推理线程数-t并发llama-bench纯CPU峰值预填充解码

这条适用于

  • llama.cpp（本例 b12600；本机 Windows 侧 b11901 亦可复现形状）
  • 一台能跑 llama-bench 的机器，最好 8 个以上逻辑核
  • 测试时尽量关掉后台重负载，否则绝对值偏低（相对关系仍成立）

具体做法

【实测口径】
模型：qwen2.5-1.5b-instruct-q4_k_m.gguf，1,117,320,736 B；三机同一文件（本机与 ARM 机从双路机内网 HTTP 取）
引擎：llama.cpp b12600 / v1.0.0-dev / commit 29b52d398（2026-11-20T23:30:28Z）；本机 Windows 侧为 b11901 / 0.7.0-dev / commit 5320c87ff
命令：llama-bench -m <model> -p 512 -n 128 -t <N> -r 2 -o csv
机器 A：Intel Core Ultra 7 270K Plus，24 逻辑核，后端 ggml-cpu-alderlake，独占无后台
机器 B：Intel Xeon E5-2673 v4 ×2（Broadwell，无 AVX-512），80 逻辑核 / 40 物理 / 2 NUMA，后端 ggml-cpu-haswell；常驻 3 台 QEMU 虚拟机合计 34 vCPU / 88GB（16+12+6），loadavg 1.17 / 8.79 / 13.45
机器 C：NVIDIA GB10 aarch64 / ARM v8.6，20 逻辑核，后端 ggml-cpu-armv8.6_2；常驻 sglang 生产服务，114% CPU / GPU 90%，loadavg 2.47 / 2.98 / 3.47

失效边界
【不许当结论的部分】
1. 80 线程崩盘的根因没定位到指标层。只知道是「线程数 + 34 vCPU 被虚拟机抢」的叠加，未采 perf / numastat / mpstat，各占多少不知道。
2. 机器 C 的绝对值按 11-18 判据应判污染（sglang 常驻 114% CPU / GPU 90%），本文只用其方向（最优线程远小于核数），不引用绝对值。
3. 跨机对比非严格同版本：本机 b11901、远端 b12600，中间差 3 天（含 11-20 的 mmap 与 IQ2 提交）。
4. 33B 模型只在机器 A 测了 24 线程一档，三机横向未做。
5. 机器 A 的单线程 stream copy 未测，三机带宽横向缺一角。
6. 线程数与功耗/温度的关系未测，崩盘过程是否含降频未知（机器 B 无 root）。
7. 机器 C 的 t≥12 未做重复测量。
8. 单线程 stream copy 是 python 纯字节拷贝、未向量化，绝对值偏低，只能做相对比较。
