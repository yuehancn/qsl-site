本地大模型搬运：大带宽单流吃不满，先加流再加窗口

性能 · 1 条边 / 6 档窗口 / 3 档并发 / 1 条千兆对照未标注整理于 2026-11-20 有效期 permanent

同一份 7,405,956,128 字节的分片，从一台 DGX Spark 经 200G 直连搬到另一台，四轮取中位。默认接收窗口下内核只给 131,072 字节（128 KB），单流只跑到 2,050.50 MB/s，占 200G 的 8.2%。把 SO_RCVBUF 调到 2 MB，提到 3,262.76 MB/s（13.1%）就到顶，再往上 4/8/16 MB 反而掉回 10.6%–12.6%。改并发才是主变量：4 流聚合 10,715.01 MB/s（42.9%），8 流 12,079.21 MB/s（48.3%）。但 8 流的单流速度从 2,678.75 掉到 1,509.90 MB/s（−43.6%），按「聚合还在涨、单流已单调降 = 链路已满」的判据，48.3% 就是这条链路的实际上限。对照那根千兆管理网：117.59 MB/s = 0.941 Gbps，占标称 94.1%，T1=T2=T4 全是 117.5x，加流完全无效。

本地部署模型搬运200GTCP接收窗口SO_RCVBUF并发流数千兆网DGX Spark

这条适用于

  • 两端同一内核版本且可修改 SO_RCVBUF
  • 发送端应尽量清空背景负载（本例无法清空）
  • 接收端逐轮校验字节数，避免把断连当完成

版本指纹

7,405,956,128 B 分片 + DGX Spark GB10 + 200G 直连

具体做法

【实测口径】
  发送端：DGX Spark #1（aarch64 GB10 / 20 核 / 122 GB 内存），源文件为生产模型真实分片，7,405,956,128 B
  接收端：DGX Spark #2 经 200G 直连；旁路对照为一台主机经千兆管理网
  服务端每连接一线程（避免串行 accept 假值）；客户端 threading.Barrier 栅栏同步起跑
  每档 4 轮取中位；每轮校验 got 字节数 == 目标字节数，不等的整档作废；单流每轮 4 GiB
【接收窗口梯度（200G 单流，4 轮中位）】
  不设（内核自动，生效 131,072 B）：2,050.50 MB/s = 16.404 Gbps = 8.2%
  1 MB（生效 2,097,152 B）：2,525.36 MB/s = 20.203 = 10.1%
  2 MB（生效 4,194,304 B）：3,262.76 MB/s = 26.102 = 13.1%（最高）
  4 MB（生效 8,388,608 B）：3,157.16 MB/s = 25.258 = 12.6%
  8 MB（生效 8,388,608 B）：2,743.76 MB/s = 21.950 = 11.0%
  16 MB（生效 8,388,608 B）：2,648.98 MB/s = 21.192 = 10.6%
【并发梯度（自动窗口，每流 4 GiB）】
  T=1：2,050.50 MB/s = 16.404 Gbps = 8.2%，单流 2,050.50
  T=4：10,715.01 MB/s = 85.720 Gbps = 42.9%，单流 2,678.75
  T=8：12,079.21 MB/s = 96.633 Gbps = 48.3%，单流 1,509.90（较 T=4 降 43.6%）
【对照通道】
  千兆管理网：117.59 MB/s = 0.941 Gbps = 94.1% 线速；T1 = T2 = T4 = 117.5x，加流无效
  本机 NVMe（O_DIRECT 16 MB × 256）：10.6 GB/s

【18.475 GB 权重搬运时间】200G 八流 1.5 s ｜ 200G 单流默认窗口 9.0 s ｜ 千兆 157.1 s（2.62 min）｜ 本机盘 1.7 s

失效边界
只测了环拓扑上一条边（Spark #1 ↔ #2），另外三条边与对角线未测（对角线没有 200G 路径），不可外推到其它边。200G 只跑到 48.3% 的根因未定位：已排除「窗口太小」这一因，但 PFC / ECN / GPUDirect / MTU / 中断绑核全部未查。窗口梯度只做到 16 MB 请求（内核封顶 8 MB 生效），未改 net.core.rmem_max，也未试 64/128 MB 档。全部测量是「网络读进内存」，没有同时写盘，所以文中秒数是纯网络值，不是端到端搬运时延。未测边下载边加载（mmap 场景）。未测跨网段。自动窗口那档四轮极差 78.4%，因发送端常驻推理服务占用背景算力，中位数可用、单次值不可引用。
