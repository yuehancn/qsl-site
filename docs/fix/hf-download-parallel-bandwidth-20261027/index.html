本地部署拉模型权重：8 线程只快 1.77 倍，卡的是链路不是线程

性能 · 2.68→4.73 MiB/s / 1.77 倍 / 每线程降至 22% / 24 档 435.40 GiB / 实测 31 分 15 秒L1整理于 2026-10-27 有效期 180d

分块并发下载能加速，但收益远低于线程数。本机对 hf-mirror.com 实测：单线程 2.68 MiB/s，并发 2/4/8 得 3.85/4.34/4.73 MiB/s，加速比 1.00/1.44/1.62/1.77 倍。关键是每条线程分到的带宽从 2.68 掉到 1.93/1.09/0.59 MiB/s —— 掉到 22% 说明总数不是线程能力，是链路容量。9.4 GiB 单线程 60 分钟、8 线程 34 分钟；实际完整下载 31 分 15 秒。

本地部署模型下载带宽量化GGUF镜像并发试错成本

这条适用于

  • 能对目标仓库发 HTTP Range 请求（镜像或 HF 均支持，返回 206 表示支持分块）
  • 磁盘剩余空间大于目标档位体积的 1.2 倍（下载中会有分块临时文件）

版本指纹

Windows 11 / hf-mirror.com / 每块 8 MiB / 并发 1-2-4-8 各三轮 / 2026-10-27 01:00-01:59

具体做法

本机实测环境：Windows 11 / hf-mirror.com / Nanbeige_Nanbeige4.3-33B-IQ2_XXS.gguf 10,071,403,648 B / 每块 8 MiB HTTP Range 请求。

【并发测速（各 3 轮取均值）】
· 并发 1：2.68 MiB/s（2.42 / 2.84 / 2.78），每线程 2.68
· 并发 2：3.85 MiB/s（3.10 / 4.33 / 4.14），每线程 1.93，加速 1.44 倍
· 并发 4：4.34 MiB/s（4.54 / 4.45 / 4.02），每线程 1.09，加速 1.62 倍
· 并发 8：4.73 MiB/s（4.81 / 4.72 / 4.67），每线程 0.59，加速 1.77 倍
· 每线程保留率：100% / 72% / 41% / 22%
· 换算：22.5 / 32.3 / 36.4 / 39.7 Mbps

【完整下载】
· 8 线程分块，10,071,403,648 B，实测 31 分 15 秒
· 按 4.73 MiB/s 理论值 33.8 分钟，实际快 2.6 分钟（短抽样含 TLS 握手与首字节等待，摊薄后略快）
· 落地字节 10,071,403,648 B 与官方仓库 tree/main 的 size 一位不差

【全档总量（bartowski 仓库 24 个单文件档，不含 bf16 两分片与 imatrix）】
· 合计 467,511,421,952 B = 435.40 GiB
· 单线程 46.2 小时 / 8 线程 26.2 小时
【试错路径成本】
· IQ2_XXS + Q2_K = 21.98 GiB → 8 线程 79 分 / 单线程 139 分
· 再加 IQ3_XXS = 35.47 GiB → 128 分 / 226 分
· Q4_K_M + Q3_K_M + IQ2_XXS = 43.57 GiB → 157 分 / 277 分
失效边界
三条边界：① 测速是单时单地单次测量，不同地区、不同时段、不同镜像差异很大，不能作为某镜像快慢的评价 ② 本机 GPU 同期有后台任务占满，但下载走的是网络与磁盘，不受影响 ③ 24 档合计体积是文件字节数直接相加，可复现；但下载时间是由测得的速度换算的估算值，不是每一档都真拉过 —— 只有 IQ2_XXS 那一档是实测 31 分 15 秒。
