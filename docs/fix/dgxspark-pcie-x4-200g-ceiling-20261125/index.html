DGX Spark 的 200G 只跑一半：不是 PFC，是网卡挂在 PCIe ×4 上

性能 · 2 台直连 / 5 个嫌疑排查 / 7 档流数阶梯 / 3 条路径对照未标注整理于 2026-11-25 有效期 180d

两台 DGX Spark 直连的 200G 聚合只有 12,414.46 MB/s（占标称 49.7%），逐项排查五个常见嫌疑：MTU 已是上限、中断一一绑核、RoCE 四项错误计数全零、PFC 反压是结果不是原因 —— **根因是 ConnectX-7 的 PCIe 链路出厂就是 ×4**（`max_link_width` 也是 4，没有更宽的状态），Gen5×4 理论 15.75 GB/s，实测已跑到它的 78.8%，属于正常工程值。**单流只有 14.3% 是另一堵墙**：`wmem_max` 封顶 4 MB，而 200G 的带宽时延积是 3.8 MB，显式放大 SO_SNDBUF 后单流 3,010.95 → 6,315.38 MB/s（+109.7%）而 4 流聚合纹丝不动 —— 两组数据同时证明「单流慢是缓冲，聚合上不去是 PCIe」。最实用的一段是端到端：纯网络 7,225.9 MB/s，边收边 O_DIRECT 落盘只剩 1,624.7 MB/s（−77.5%），而本机盘单独写有 10,722.3 MB/s，**盘不是瓶颈，是「收一块写一块」没有重叠**。结论落到钱上：18,475 MB 的模型，本机 1.7 秒 / 200G 端到端 11.6 秒 / 千兆 157.1 秒，**插上 200G 比 1G 快 13.5 倍，不是快 200 倍**；指望它当单台 200G 存储节点，方向从采购那天就错了。

这条适用于

  • Linux，能读 lspci -vv 与 ethtool -S（部分计数需 root）
  • 两台机器之间已有 200G 直连或交换机通路
  • 测时机器上可能还跑着别的负载，需在结论里声明

版本指纹

mlx5_core 7.0.0-1019-nvidia / 固件 28.45.4028 / mtu 9000 / 200G 直连

具体做法

【实测口径】
  机器：两台 DGX Spark 直连（不走交换机），驱动 mlx5_core 7.0.0-1019-nvidia / 固件 28.45.4028
  链路：speed=200000 / mtu=9000；测时两台均在跑 sglang（GPU 90-91%），属带污染测量，数值取下限
  测法：自写 socket（不套 iperf3），可同时控制流数 / 每流字节数 / SO_SNDBUF
【第一组：PCIe 宽度（全文根因）】
  LnkCap: Port #0, Speed 32GT/s, Width x4
  LnkSta: Speed 32GT/s (ok), Width x4 (ok)
  max_link_width = 4 → 出厂就是 ×4，没有更宽的状态
  PCIe Gen5 ×4 理论 = 32 × 4 × (128/130) ÷ 8 = 15.75 GB/s
  200G 以太网理论 = 25 GB/s → 链路设计上只能装进 63%
  实测聚合峰值 12,414.46 MB/s ÷ 15.75 GB/s = 78.8%（正常工程值，已压满）
【第二组：并发梯度复测（512 MiB/流）】
  T=1   3,574.31 MB/s  28.595 Gbps  14.3%   单流 3,574.31
  T=4  11,899.71 MB/s  95.198 Gbps  47.6%   单流 2,974.93
  T=8  12,414.46 MB/s  99.316 Gbps  49.7%   单流 1,551.81
  vs 11-20 同口径 12,079.21 → 误差 +2.8%（复现度够，可当定论）
【第三组：五个嫌疑逐条排查】
  MTU           接口 9000 / RoCE active_mtu 4096     → 已是上限，不是根因
  中断绑核       20 个 MSI 队列，363→核0 … 383→核19 一一打散 → 教科书配置，不是根因
  RoCE 错误计数  xmit_discards / rcv_errors / xmit_wait / buffer_overrun 全 0 → 链路无损
  PFC           rx_pause_ctrl_phy 本机 5,192 / 对端 685  → 反压是结果不是原因
  PCIe          宽度 ×4，上限 ×4                      → 就是它
【第四组：单流缓冲对照（512 MiB/流）】
              默认缓冲      显式 4MB      变化
  T=1        3,010.95      6,315.38     +109.7%   ← 单流翻倍
  T=4       12,429.07     11,542.36      −7.1%    ← 聚合纹丝不动
  T=8       11,587.92     11,101.29      −4.2%
  wmem_max = 4,194,304 B；tcp_rmem 最大 33,554,432 B（收发不对称 8 倍）
  RTT min 0.152 ms → BDP = 200 Gbps × 0.152 ms = 3.8 MB，正好被 4 MB 封顶
【第五组：流数阶梯（128 MiB/流，显式 4MB）】
  T      2         3         4         6         8        12        16
  聚合  5,075.76  8,515.91 12,429.07 9,498.01 11,587.92 10,283.87 11,107.71 MB/s
  单流  2,537.88  2,838.64  3,107.27 1,583.00 1,448.49   856.99    694.23 MB/s
  ⇒ 聚合 4 流后不再涨、单流单调跌 = 链路满了
【第六组：端到端落盘（512 MiB/流，18,475 MB）】
  纯内存接收    T=1 7,225.9 / T=4 6,131.6 MB/s
  边收边落盘    T=1 1,624.7（−77.5%）/ T=4 1,637.8 MB/s
  本机 NVMe O_DIRECT 写  10,722.3 MB/s（1 GiB / 0.100 s）→ 盘比网络快 6.6 倍
【第七组：同一批数据的三种搬法】
  本机 NVMe 复制                1.7 s    1×
  200G 直连 + 落盘   ≈ 11.6 s   6.8×
  千兆管理网 117.59 MB/s        157.1 s  92×
  ⇒ 插上 200G 比 1G 快 13.5 倍，不是快 200 倍
【口径说明】
  · 78.8% / 63% / 6.6 倍 / 13.5 倍 均为两个已入库实测值的算术派生，非直接测量。
  · 11.6 秒 = 18.475 GB × 1024 ÷ 1,624.7 MB/s，按实测落盘速率反推，非直接计时。
  · 512 MiB 与 128 MiB 两组口径不同，绝对值不可横比，只看各自走势。
失效边界
1.  两台全程在跑 sglang（GPU 90-91%），所以只能说「两台都在跑推理的 DGX Spark 上 200G 聚合到 11.5–12.4 GB/s」，不能写「DGX Spark 的 200G 上限是 12 GB/s」。空载可能更高，但最高也只能逼近 15.75。
2.  验证「×4 是硬上限」最干净的方法是跑 RDMA 绕开 TCP 栈，本次没做。所以「15.75 GB/s 是物理上限」这个结论建立在  的自证上，而不是「另一条路径也撞同一堵墙」的交叉验证。
3.  只验证了四台机器的 PCIe 配置同为 ×4，没测其他三条链路的实际聚合吞吐，不能假设它们也正好 48-50%。
4.  需要 root，本次只用到 4 MB 这个已有上限，没验证「放开到 16 MB 后单流还能不能再涨」。
5. ，未测多流并发落盘与 io_uring。如果你用 io_uring 或双缓冲，1,624.7 MB/s 这个数会变好，具体多少未测。
6. ，未与 NVIDIA 官方规格页交叉核对。
