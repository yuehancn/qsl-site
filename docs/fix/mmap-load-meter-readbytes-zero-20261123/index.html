mmap 加载计量：扫完 1 GiB，read_bytes 还是 0

性能 · 1 GiB 测试文件 / 16 页 vs 262144 页 / 4 档块大小 / 冷热两态未标注整理于 2026-11-23 有效期 180d

判断本地模型加载慢不慢，大多数人用的 `/proc/self/io` 的 read_bytes —— 而它根本不统计 mmap 路径。实测：mmap 只读头 4 KB 报 0；**全量扫完 1 GiB 依然报 0**。同一时刻用 pagemap 的 present 位逐页数，只碰 4 KB 是 16/262,144 页（0.0625 MiB），全量扫是 262,144 页（1,024 MiB）。两个数都为真：mmap 确实没偷读全文件（这句是对的），但 read_bytes 也真的量不到它（这句是错的源头）。有效判据只有 pagemap 驻留页。另有三个附带的坑：MADV_WILLNEED 会先花 302.27 ms 却留下 0 驻留页；4 KB 块步长比 64 KB 峰值低 44%；macOS 上首次碰 4 KB（97.821 ms）比扫完 1 GiB（64.350 ms）还慢 1.520 倍，因为首次触碰付的是固定开销而不是体积开销。

mmapread_bytespagemap模型加载存储IOOllamallama.cpp磁盘加载慢排查

这条适用于

  • Linux，需 root 或 CAP_SYS_ADMIN 才能读 /proc/self/pagemap
  • macOS 做对照时无 root 无法 purge，冷态数字不纯

版本指纹

Ubuntu 26.04.1 / glibc 2.43 / python 3.14 / page 4096B；macOS 27.2.1 / page 16384B

具体做法

【实测口径】
  Linux 机：CPU02 计算节点 = Xeon E5-2673 v4 ×2 / 80 逻辑核 / 126 GB / Ubuntu 26.04.1 / glibc 2.43 /
            python 3.14 / page size 4,096 B
  macOS 机：Mac mini M6 = Apple M6 12C / 16 GB 统一内存 / macOS 27.2.1 / page size 16,384 B
  测试对象：1 GiB（1,073,741,824 B）`\xa5` 填充单文件，fsync 落盘
  清缓存：posix_fadvise(POSIX_FADV_DONTNEED)，清完用 pagemap 驻留页复核
【第一组：同一动作，两把尺子（CPU02 计算节点，1 GiB 文件）】
  用例                        驻留页(pagemap)      read_bytes
  mmap 只读头 4KB             16 页 / 0.06 MiB          0
  mmap + MADV_RANDOM 读 1 页  16 页 / 0.06 MiB          0
  pread 只读头 4KB            —                        0
  mmap 全量扫 1 GiB           262,144 页 / 1,024 MiB    0
  ⇒ 全量扫完 1 GiB，read_bytes 依然是 0。这就是「没测到」被当成「没读」。
【第二组：MADV_WILLNEED 反直觉】
  mmap + MADV_WILLNEED → 驻留 0 页，耗时 302.27 ms
  对照：只读头 4 KB → 16 页，耗时 0.09 ms
  ⇒ 预读建议先花 300 ms，然后你还是要等真正的页错误。
【第三组：块大小阶梯（CPU02 计算节点，512 MiB 顺序读，page cache 命中口径）】
  4 KB  → 2,048.1 MB/s
  64 KB → 3,684.9 MB/s  ← 峰值
  1 MB  → 3,419.1 MB/s
  4 MB  → 3,473.8 MB/s
  4 KB 相对峰值低 44.4%
【第四組：macOS 冷态（Mac mini M6，1 GiB 文件，page size 16,384 B）】
  首次 mmap 只读头 4 KB  →  97.821 ms（Pageins +1）
  紧随其后全量扫 1 GiB   →  64.350 ms（Pageins +1）
  热态 mmap 只读头 4 KB  →   2.809 ms
  热态全量扫 1 GiB       →  46.989 ms
  首次头 4KB ÷ 首次全扫 = 1.520×（碰 4KB 比扫完 1GiB 还慢）
【口径说明】
  · 9,269 MB/s 是 page cache 命中下的扫读速度，不是磁盘顺序读带宽。
  · 驻留比例 = 驻留页 ÷ 总页数；体积 = 驻留页 × page size。
  · Mac 侧无 root 无法 purge，冷态含缓存污染，97.8 / 64.4 只作方向性证据。
  · 测试对象是填充文件，不是 GGUF；llama.cpp 实际加载路径未在本轮复现。
失效边界
1.  测的是  填充的 1 GiB 文件，不是 llama.cpp 加载 GGUF 的真实路径。
要复现 11-20 那个 mmap 社区问题，得装 llama.cpp + 准备一个 GGUF 且超出 page cache，本轮时间盒不够。
所以本文能说「mmap 的计量口径是这样」，不能说「你加载 GGUF 慢就是这个原因」。
2.  观察到的是实测现象 + 通行解释（只统计块设备层实际 IO，页错误走另一条路）。标为「实测现象」，不当内核机制讲。
3.  无 root 不能 purge，文件刚写完可能部分仍在缓存里。
97.821 / 64.350 这个比例只当方向，别当保证的绝对值。
4.  只跑了单轮，且文件在缓存中（4k 0.11s / 64k 0.02s / 1m 0.01s）， ⚠️ 仅作方向性旁证，不可引用为实测结论。
5.  本文结论以 Ubuntu 26.04.1 实测为准， 换发行版请自己复算一遍。
6.  那篇是另一种测法（读方向与文件布局不同），本篇 4 MB 反而比 64 KB 低 5.7%。两次独立观测，别合并引用。
